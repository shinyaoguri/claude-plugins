# 0017: 人間の承認はプラン 1 点へ集約し、実行時の安全は分類器と決定論的フックで担う

- **状態**: 採用 (2026-08-12。印の置き場は 2026-08-16 に訂正 — 下の「訂正: 印はリポジトリでなくセッションに属する」)

- **文脈**: 承認プロンプトの位置が実態と逆になっていた。ブランチ削除やスクリプト実行のたびに確認が出る一方 (実質 OK を押すだけで、押す前に判断材料が増えるわけではない)、本当に方向性を確かめたい「実装に入る前」には何のゲートも無い。可逆な操作に確認を挟んでも安全性は上がらず、確認疲れで**本当に見るべき 1 回まで反射で押す**ようになるのが最大の害だった。

  調査で分かった構造 (Claude Code v2.1.220):

  - 承認を消す本体は **auto mode**。分類器モデルが全ツール呼び出しを審査し、要求を超える操作・未知のインフラ宛て・読んだ内容に誘導された操作を止める。2026-08-14 から Pro / Max / Team の新規セッションで既定になる
  - 分類器の設定 (`autoMode.{environment,allow,soft_deny,hard_deny}`) は **`~/.claude/settings.json` と managed settings からしか読まれない**。プロジェクトの `.claude/settings.json` もプラグインの `settings.json` も対象外で、これは意図的な仕様 — リポジトリ側から読めば、clone したリポやビルド手順が自分に都合のよい allow を注入できてしまう。プラグインの `settings.json` が受け付けるキーも `agent` と `subagentStatusLine` だけ
  - つまり**プラグインはこの層を供給できない**。供給できるのは hooks で、`PreToolUse` は `allow` / `deny` / `ask` / `defer` を返せる
  - 公式が Danger で警告している落とし穴がある: `autoMode` の配列を `"$defaults"` 無しで書くと、その節の組み込みルール (force push・`curl | bash`・本番デプロイ・データ持ち出し・auto-mode bypass) を**丸ごと捨てる**。緩めた自覚が残らないまま守りが消える

  [ADR 0007](0007-guardrail-visibility.md) の結論 — 実際に起きやすい暴走は権限を要する破壊ではなく**目的をショートカットする改変**である — をここにも当てる。合意なしに実装が広がることは、まさにその失敗モードの入口にあたる。

- **決定**: **人間の確認をプラン承認 1 点へ集約する**。実行時の安全は 4 層で担い、層ごとに置き場を分ける。

  | 層 | 置き場 | 担うもの |
  |---|---|---|
  | `permissions.ask` | setup リポ | 必ず人間に返す境界 = **取り返しのつかない削除だけ** (リポ・リリース・タグ)。分類器より前に評価され auto モードでも確実にプロンプトになる |
  | 決定論的フック | setup リポ (git 安全) / **プラグイン (エージェントの振る舞い)** | 構文とリポジトリの状態から機械的に判定できるもの。[ADR 0016](0016-agent-behavior-hooks-in-plugin.md) の線引きを踏襲 |
  | 分類器 (`autoMode`) | setup リポのみ | 残り全部の意味判定。**プラグインからは供給不可** |
  | 診断 (`env-doctor`) | プラグイン | 上 3 層が実際に効いているかの定期検査 |

  プラグイン側の第 1 号として **plan-gate** を置く (`hooks/scripts/plan-gate.sh` + `plan-gate-mark.sh`)。承認済みプランが無いまま編集が閾値のファイル数 (既定 3) へ広がった時点で `deny` を返し、`EnterPlanMode` へ差し戻す。`ExitPlanMode` が通れば `PostToolUse` が印を置き、以降そのセッションでは黙る。

  - **`ask` でなく `deny`** — 消したかった OK ボタンをここで作らない。`ask` にすると「押せば進める」逃げ道が残り、結局プランを書かずに済んでしまう
  - **閾値方式** — 止めたいのは「合意なしに実装が広がる」ことであって 1 ファイルの手直しではない。タイポ修正までプランを書かせると、今度はプランの側が形骸化する
  - **数えるのは作業ツリー内の実ファイルだけ** — プランファイル・スクラッチパッド・`.git` 配下・リポ外はいずれも作業ツリーの外にあるので、除外リストを育てずに済む
  - 逃げ道は `RS_PLAN_GATE=0` と `RS_PLAN_GATE_THRESHOLD`

  **訂正: 印はリポジトリでなくセッションに属する** (2026-08-16)

  当初は印を `<git-common-dir>/claude-plan-gate/<session_id>.approved` へ置いていた。worktree と親リポで同じ場所を指させるための選択だったが、置き場をフック JSON の `.cwd` から導いていたのが誤りだった。**`.cwd` は Bash ツールの永続 cwd を反映して動く**ため、`ExitPlanMode` が通った瞬間にたまたま別リポへ `cd` していると、印がそのリポの `.git` へ落ちる。実際に metaphor-sketches の worktree で作業中のセッションが、承認の瞬間だけ cwd が metaphor 側にあったため印を metaphor の `.git` に置き、**承認済みのまま 3 ファイル目で `deny` された**。

  承認は「このセッションで方向性の合意が取れた」という**セッションの事実**であって、リポジトリの事実ではない。置き場を `${CLAUDE_CONFIG_DIR:-~/.claude}/plan-gate/<session_id>.approved` へ移し、`plan-gate-mark.sh` から cwd と git の参照を丸ごと落とした (バグの発生源ごと消える)。逃げ道として `RS_PLAN_GATE_DIR` を足し、印は 30 日で掃除する。

  - **台帳 (`<session_id>.files`) は `.git` 配下に残す**。数えているのは「そのリポの作業ツリー内で触ったファイル」で、記録の前に `toplevel` 配下判定を通っているため cwd ドリフトの影響を受けない。置き場が承認印と非対称なのは意図したもの
  - 移行用の後方互換パスは足さない。プラグイン更新はセッション再起動を伴い、最悪でもプランを出し直すだけで済む
  - 誤爆したときに気付けるよう、`deny` の文面へ**印の置き場と、そこに無いこと**を出す。「承認したのに差し戻された」ときに何を見に行けばよいかが文面だけで分かる

  診断側では **`env-automode-defaults` を required** に置く。`"$defaults"` の欠落は「守りが消えたのに誰も気付かない」唯一の形で、この層で最も費用対効果が高い検査だから。

- **影響**: 可逆な操作の確認は消え、確認は方向性を決める 1 点に残る。plan-gate はプラグインを有効にした**全プロジェクトで動く**ため、小さな作業を妨げないことが要件になる (閾値未満・plan モード・リポ外・git 管理外・`RS_PLAN_GATE=0` はすべて無出力で素通し)。判定は [scripts/test-rs-plan-gate.sh](../../scripts/test-rs-plan-gate.sh) が PR CI で検証する (30 assertions。使い捨て git リポへ hook の JSON を直接流し、終了コードと `permissionDecision` を確認する。linked worktree・無関係な別リポ・git 管理外の cwd から承認しても印が効くことも、実際に `git worktree add` したリポで確かめる)。

  既知の限界:

  - **ファイル数は「合意が要る規模か」の代理指標にすぎない**。1 ファイルに閉じた大改造は素通りし、無関係な 3 ファイルの typo 修正は止まる。より正確な指標 (差分行数・新規ファイルか既存かの区別) は誤判定の形が変わるだけで単純に良くはならないので、まず素朴な形で実地に投入して調整する
  - **印はセッション単位**。`--resume` で再開したセッションは同じ `session_id` を持つので引き継がれるが、`/clear` 後は数え直しになる。30 日を過ぎた印は次の承認時に掃除されるので、それより後に再開したセッションもプランを出し直すことになる
  - **セッションが複数リポを触る場合、どこか 1 つでプランを承認すれば全リポで黙る**。上の訂正どおり承認をセッションの事実として扱う以上これは帰結で、止めたい失敗モード (合意なしに実装が広がる) はセッション単位で起きるため実害は小さいと判断した
  - 分類器の層はマシン設定に依存するため、**設定が入っていないマシンではこの ADR の半分しか効かない**。だからこそ `env-doctor` に診断を置いた
