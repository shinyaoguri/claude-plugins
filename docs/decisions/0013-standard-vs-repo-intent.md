# 0013: 標準は全リポ共通の既定であり、リポ固有の設計意図との衝突を監査が判定する

- **状態**: 採用 (2026-08-07)
- **文脈**: [0012](0012-audit-precision.md) で本監査の判定精度を上げたが、**「標準に合っていない」ことと「直すべき」ことを同一視したまま**だった。repo-standards.json は 1 人の開発者が全リポに共通して適用したい既定であって、個別のリポで最適とは限らない。

  現行の監査に、意図的な逸脱を認識する仕組みは無かった (実測で確認):

  - **機械判定 43 項目は完全に二値**。分岐は `applies_to` (リポ種別) と `when.visibility` の 2 つだけで、`when` を持つ項目は 4 件・すべて visibility。リポ固有の設計意図は入力にすら入らない
  - **LLM 判定 6 項目の `skip`** は「判定観点が定義した対象外条件」専用で、「このリポでは意図的にこうしている」は skip の理由にならない
  - **正本のスキーマに例外の枠が無い** (`applies_to` / `check` / `fix` / `id` / `layer` / `level` / `when` / `why`)

  唯一の受け皿は `decision: rejected` だが、これは人が却下したときだけ動き、findings は `.git` 配下のマシンローカルで、clone し直せば消え他マシンへ伝搬しない。つまり**「このリポではこれが正しい」という判断を、毎回ゼロから人が言い直していた**。

  このリポ自身に生きた例がある。`contributing-exists` の `why` は「public リポの外部協力者向けの入口。**個人リポでは CLAUDE.md が兼ねる場合もある**」と例外を明文で予期しているのに、判定は WARN、fix は「CONTRIBUTING.md を追加する」。標準が自分で認めている逸脱すら判定できていなかった。

- **決定**:

  1. **標準を既定として扱い、衝突判定の層を足す**。`ng` / `warn` になった項目に対して、その fix を当てるとリポ自身が明示している設計意図と衝突しないかを判定し、`intent` (`aligned` / `unclear` / `conflicts`) と理由を findings に記録する
  2. **機械判定 43 項目も対象に含める**。これらは LLM を通らないので、**衝突判定が文脈を持ち込める唯一の接点**になる。ここを LLM 判定だけに限ると、標準の大部分が二値のまま残る
  3. **`intent` は `verdict` を上書きしない**。標準から外れているという事実と、それがこのリポでは正しい逸脱かもしれないという文脈は別物で、後者で前者を消すと「外れていること」自体が集計から消える。`conflicts` でも `ng` は `ng`、未決は未決のまま残り、扱いを変えるのは repo-audit-fix の側
  4. **衝突と言えるのはリポにコミットされた記述に根拠があるときだけ**。CLAUDE.md・ADR・README・設定ファイルを指せないなら `aligned` か `unclear`。「無い方が楽」「このリポには要らない気がする」は衝突ではない。ここを緩めると**標準を黙らせる装置**になり、従うのが面倒な項目ほど `conflicts` が付いて逸脱が理由なく常態化する
  5. **判断の理由を必須にする** (`--intent-note`、20 バイト以上)。理由なしに `conflicts` が付くと、修正フローが「なぜ当てないのか」を説明できないまま項目を提示のみに落とすことになる
  6. **意図の材料は 1 回集めて使い回す** (`rs-evidence.sh --intent`)。CLAUDE.md 全文・CONTRIBUTING・README の見出し・ADR 一覧・as-code 管理されている設定で、項目ごとに変わらないため。実測 2.4K トークン
  7. **衝突判定は HEAD では陳腐化させない**。設計意図はコミットごとに変わるものではなく、毎回無効化するとコストが跳ねるだけ。項目が標準に適合すれば `intent` は自動で落ち、設計意図そのものが変わったときだけ付け直す
  8. **repo-audit-fix は `conflicts` を群 3 (提示のみ) へ落とす**。`unclear` は元の群のまま、ただし承認時に理由を必ず併せて提示する — 判断材料を伏せたまま承認させない
  9. **逸脱が積み重なるなら、直すべきは標準の方**。`conflicts` が続く項目は setup リポ (`claude/repo-standards.json`) の Issue へ持っていく導線を repo-audit-fix に書く

- **影響**: findings の行スキーマに `intent` / `intent_note` が増え、repo-standards は minor bump になる。監査は判定 → 反証 → 衝突判定の 3 段になり、コストは指摘件数ぶん増える (材料は共通なのでサブエージェント 1 本あたりは小さい)。プラグインのエージェントは 4 個になる。

  **この仕組みは「逸脱の記録」までしか担わない。** 判断はマシンローカルの findings にしか残らず、他マシン・他人・再 clone を越えない (repo-audit-fix の PR 本文に載せる運用で部分的に補う)。逸脱をリポにコミットして持続させる waiver 方式は、この衝突判定が「人が気づかなくても指摘してくる」役目を果たしてから、実際に何が繰り返し `conflicts` になるかを見て設計する ([#65](https://github.com/shinyaoguri/claude-plugins/issues/65))。先に waiver を作ると、何を免除すべきか分からないまま免除の器だけができる。
