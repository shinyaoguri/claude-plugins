# 0021: グローバル / plugin / リポジトリ の三層 — 置き場は「どこで発火する必要があるか」で決める

- **状態**: 採用 (2026-08-31)

- **文脈**: [#144](https://github.com/shinyaoguri/claude-plugins/issues/144) が「グローバルに効く設定を最低限にし、支援はリポ側へ寄せたい」と提起した。先行実例は [mokume](https://github.com/mokume-metal/mokume) で、あちらは [ADR-0017](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0017-agent-support-locality.md) で「エージェント支援はリポジトリで完結させる」と決め、`repo-standards` の宣言を畳んでいる。動機は実害で、承認待ちで意図的に赤い PR を個人環境のフックが故障と見て 3 回鳴った ([#140](https://github.com/shinyaoguri/claude-plugins/issues/140) / [#141](https://github.com/shinyaoguri/claude-plugins/issues/141) / [#145](https://github.com/shinyaoguri/claude-plugins/issues/145))。**リポジトリ固有の設計を、それを知らない外側の機構が判定していた**わけである。

  メンテナの決定で方針が確定した — 「グローバルな `settings.json` にしか書けないものは残し、それ以外は全てそれぞれのリポジトリへ移す」。

  ところがこの基準をそのまま当てると切れないものが 3 つ残った ([shinyaoguri/setup#127](https://github.com/shinyaoguri/setup/issues/127) / [mokume-metal/mokume#499](https://github.com/mokume-metal/mokume/issues/499) の論点):

  - **公開面に書けないルールを持つ支援**。`term-guard` のルール (どのリポジトリでどの語を禁じるか) は新旧リポジトリの対応関係という機微情報で、public なリポジトリには置けない。「書ける場所が無い」点は分類器の設定と同じだが、理由が違う
  - **リポジトリに属さない場面を守る支援**。`git-safety-guard` を各リポへ移すと、clone する前・`~/` 直下・リポジトリでないディレクトリでの破壊的操作が無防備になる。移した先ごとに写しが増える点も擦れる
  - **支援ではなく個人の道具立て**。statusLine・計測・言語サーバ・ブランチ掃除は、[0020](0020-skills-ship-as-plugins.md) 決定 2 の「プラグインから供給できない層」に形の上では当たらないが、そもそも**リポジトリの支援ではない**

  3 つに共通するのは、**「どのファイルに書けるか」を基準にしていること**である。それは設定ファイルの仕様の話で、その支援が守っている場面とは別のことを言っている。基準を差し替えると 3 つとも同じ規則で解ける。

- **決定**:

  1. **置き場は「どこで発火する必要があるか」で決める。** 上から順に当て、最初に当たった段が置き場になる:

     | 段 | 条件 | 置き場 |
     |---|---|---|
     | 1 | 仕様上グローバルにしか書けない | [setup](https://github.com/shinyaoguri/setup) の `claude/settings.json` |
     | 2 | 守る場面がリポジトリの外にある / ルールを公開面に置けない | setup の `claude/` (最小の安全網) |
     | 3 | リポジトリの中でしか発火しない | そのリポジトリの `.claude/` |

     段 2 に来るのは「移し先が無いもの」ではなく「**守る場面がそこに無いもの**」である。`git-safety-guard` は clone する前にも効く必要があり、`term-guard` は機構とルールを分離した時点で公開リポジトリを置き場から外している。段 1 との違いは理由だけで、結論は同じ。

  2. **plugin 層が持つのは「リポジトリが要求しない汎用支援」である。** 段 3 に落ちたもののうち、リポジトリの規約が**要求しない**支援 — 各自が入れて各自に効くもの — は plugin として配る。[0020](0020-skills-ship-as-plugins.md) 決定 3 の 3 基準 (hooks・agents・scripts を伴う / enable・disable の単位を持つ / version をまたいで伝搬を制御したい) は変えない。

     ここが [0016](0016-agent-behavior-hooks-in-plugin.md) の位置づけを変える。`plan-gate` / `ci-watch` / 各種 sweep は**個人が使う支援であって、リポジトリが要求するものではない**。要求されていないので、リポジトリはそれを前提にしてよい規約を書けない。逆に言えば、あるリポジトリが同じことを**要求する**と決めたら、そのときは段 3 に落ちてリポ側が実体を持つ (mokume の ADR-0017 決定 3 の改訂がその形)。

  3. **特定のリポジトリでしか使わないプラグインの宣言は、そのリポジトリへ移す。** グローバルの `enabledPlugins` / `extraKnownMarketplaces` に残すのは、**どのリポジトリのものでもない**宣言だけにする。

     ただし**要求と道具を混ぜない**。リポジトリが宣言してよいのは、そのリポジトリを触る人の手元を楽にする**道具** (技術ドキュメント・補完) までで、**リポジトリの規約を判定する支援を宣言してはならない**。後者を宣言すると「入れている人にだけ規約が効く」状態に戻り、mokume の ADR-0017 決定 2 が畳んだものが復活する。

  4. **個人の道具立ては移行対象ではない。** statusLine・計測・言語サーバ・セッション終了時のブランチ掃除は、**移し先が「どれか 1 つのリポジトリ」にならない**。特定のリポジトリに属さないので段 3 に落ちようがなく、グローバルに残る。

     言語サーバがこの型の分かりやすい例になる。Swift のリポジトリは手元に 8 本あり、そのうち mokume は ADR-0017 決定 2 によって `enabledPlugins` を**書けない**。リポ側へ移すと mokume だけが道具を失うか、あちらの決定を曲げるかになる。どちらも筋が悪い。

- **影響**: [0020](0020-skills-ship-as-plugins.md) 決定 2 は「setup が持つのはプラグインから供給できない層に限る」と書いていた。本 ADR の決定 1 がその判定を置き換える — 供給できるかどうかではなく、どこで発火する必要があるかで決まる。0020 の残り (決定 1・3・4) は動かない。

  [0016](0016-agent-behavior-hooks-in-plugin.md) は「エージェントの振る舞いを縛るフックはリポにコミットせずプラグインが供給する」と決めた。決定 2 がその**適用範囲**を狭める — プラグインが供給するのは、リポジトリが要求しない支援に限る。リポジトリが要求すると決めたものは、そのリポジトリが実体を持つ。0016 の帰結 (個人標準に項目を足さない・無音の欠落が起きない・version bump で伝搬する) はそのまま残る。

  実際の移動は 3 リポジトリに分かれる。この ADR は基準だけを持ち、何がどこへ動いたかの記録は各リポジトリの Issue が持つ ([#144](https://github.com/shinyaoguri/claude-plugins/issues/144) / [shinyaoguri/setup#127](https://github.com/shinyaoguri/setup/issues/127) / [mokume-metal/mokume#499](https://github.com/mokume-metal/mokume/issues/499))。**この判断が「何を持っているか」に依存しない**ようにするためで、手元の構成が変わっても基準は読み直さなくてよい。
