# 0011: 監査はトークンコストで階層を分け、簡易版は findings を持たない

- **状態**: 採用 (2026-08-07)
- **文脈**: repo-audit の実測コストを見積もったところ、内訳が大きく偏っていた。

  - 機械判定 43 項目は全部スクリプト内で完結し、LLM が読むのは出力の JSON Lines だけ (実測 51 行 / 8.2KB ≒ 2.4K トークン)。**項目数を増やしてもここは伸びない**
  - LLM 判定 6 項目が支配的。ADR 全文・CLAUDE.md・`.claude/` 配下を読むため、判定材料だけでこのリポでは約 12K トークン (うち ADR が 9K)。これを項目ごとのサブエージェントに配ると、累積で 300〜600K に達する
  - つまり「ちょっと標準から外れていないか見る」だけの用途に、本監査は 2 桁分不相応に高い。高いから起動をためらう → 監査しなくなる、が実害

  一方、単に本監査へ `--quick` のようなフラグを足す案は採れない。スキルは SKILL.md を読み込んだ時点で手順全体がコンテキストに載り、`status: "manual"` の項目とその判定観点 (プロンプト全文) も findings 経由で流れ込む。**分岐で安くなるのは実行だけで、読み込みは安くならない**。

- **決定**:

  1. **トークンコストで階層を分ける**。`repo-audit-min` (機械判定のみ) と `repo-audit` (LLM 判定込みの本監査) を別スキルにする。[0010](0010-audit-fix-handoff.md) の分割基準「別々に起動される実ユースケースがあるか」を満たす — 日常の点検 / 多数リポの連続チェック / 本監査の前哨、はいずれも本監査とは別の起動理由
  2. **簡易版は findings を保存しない**。manual 項目を判定しないまま `rs-findings.sh save` を通すと、前回の `verdict` / `decision` を「判定していない状態」で上書きしうる。安さのために監査の記憶を壊すのは本末転倒なので、簡易版は triage 専用と割り切り、修正フロー (repo-audit-fix) への引き渡し口を持たない
  3. **簡易版の出力は JSON Lines でなく圧縮テキスト**にする。`rs-lib.sh` の出力契約の唯一の例外で、`rs-audit-min.sh` が JSON Lines を畳む出口として振る舞う。逸脱した項目だけを 1 行、detail は既定 60 文字で切り詰め、ヘッダ・集計・次アクション各 1 行。逸脱 2 件で 5 行 / 388 バイトを実測
  4. **安さを文書でなくテストで守る**。`test-rs-audit-min.sh` が「ok / skip / manual を行に出さない」「detail を切り詰める」「出力が 700 バイト未満」を検証する。ここが緩めば簡易版である意味が消えるため、行数・バイト数まで含めて固定する
  5. **コスト目安を README に書く**。スキルの説明だけでは高い方を選び続けてしまう。3 スキルの「何をするか」と実測ベースの目安を並べ、使い分けの判断材料を利用者側に置く

- **影響**: repo-standards のスキルは 7 個になる ([0009](0009-plugin-granularity.md) の再議論しきい値は 8 — 次に増やすときは分離の是非を先に議論する)。`rs-lib.sh` の出力契約に例外ができたため、以降 rs-*.sh を足すときは「JSON Lines を出すか、JSON Lines を畳む出口か」を明示する。簡易版で NG が出ても修正へは直行できず本監査を経由するが、これは意図した非対称 (安い監査が承認フローを飛ばして修正を始められると、判定材料を読まないまま直すことになる)。LLM 判定の材料が増え続ければ本監査のコストはさらに伸びるので、判定観点を正本 (setup リポ) 側で肥大させないことが前提になる。
