# 0011: 監査はコストで階層を分け、安い層は「LLM を外す」でなく「LLM の使い方を変える」

- **状態**: 採用 (2026-08-07)
- **文脈**: repo-audit の実測コストを見積もったところ、内訳が大きく偏っていた。

  - 機械判定 43 項目は全部スクリプト内で完結し、LLM が読むのは出力の JSON Lines だけ (実測 51 行 / 8.2KB ≒ 2.4K トークン)。**項目数を増やしてもここは伸びない**
  - LLM 判定 6 項目が支配的。ADR 全文・CLAUDE.md・`.claude/` 配下を読むため、判定材料だけでこのリポでは約 12K トークン (うち ADR が 9K)。これを項目ごとのサブエージェントに配ると、累積で 300〜600K に達する
  - つまり「ちょっと標準から外れていないか見る」だけの用途に、本監査は 2 桁分不相応に高い。高いから起動をためらう → 監査しなくなる、が実害

  一方、単に本監査へ `--quick` のようなフラグを足す案は採れない。スキルは SKILL.md を読み込んだ時点で手順全体がコンテキストに載り、`status: "manual"` の項目とその判定観点 (プロンプト全文) も findings 経由で流れ込む。**分岐で安くなるのは実行だけで、読み込みは安くならない**。

  当初は安い層から LLM 判定を丸ごと外す設計にした。だがそれは 6 項目 (うち 2 件が required — ADR の網羅性と作業ログの外部化) を機械判定だけでは代替できないまま落とすことになり、簡易監査の守備範囲としては狭すぎた。**コストの正体は「LLM を使うこと」ではなく「LLM に探索させること」だった** — 判定材料を集める ls・git log・gh・ファイル読みは全部決定論的に書ける。

- **決定**:

  1. **コストで階層を分ける**。`repo-audit-min` (安い一括判定) と `repo-audit` (深い個別判定) を別スキルにする。[0010](0010-audit-fix-handoff.md) の分割基準「別々に起動される実ユースケースがあるか」を満たす — 日常の点検 / 多数リポの連続チェック / 本監査の前哨、はいずれも本監査とは別の起動理由
  2. **安い層でも LLM 判定は落とさない。代わりに 3 つの手で削る**:
     - **材料を先に畳む** (`rs-evidence.sh`)。ADR の状態行・`git log`・open Issue・設定ファイルの構造を機械的に集めて渡す。12K → 約 4.8K トークンに縮み、判定側は探索のためのツール呼び出しをほぼしなくなる
     - **サブエージェントを 1 本に束ねる**。1 本ごとに固定の初期コンテキスト (system prompt + ツール定義) を払うので、6 本に割るとその分が丸ごと 6 重になる。項目ごとの並列は本監査の作法であって、安い層では逆効果
     - **Haiku 4.5 を使う** ($1/$5 per MTok。Opus 5 の 5 分の 1)
  3. **落とすのは判定の深さで、判定の有無ではない**。判定係が開けるファイルは 3 件までに制限する。ADR の決定内容と実装の乖離のように全文の突き合わせが要る観点は本監査に劣ることを、スキル本文と README に明記する
  4. **秘密情報は材料に載せない**。`.mcp.json` / `settings.json` はキー名と「環境変数参照かリテラル直書きか」だけを渡す。直書きの検出に値そのものは不要で、渡せば判定のためだけに秘密をサブエージェントのコンテキストへ持ち出すことになる
  5. **簡易版は findings を保存しない**。安いモデルの判定で、前回 repo-audit が付けた `verdict` / `decision` を上書きしないため。修正フロー (repo-audit-fix) への引き渡し口を持たない
  6. **簡易版の出力は JSON Lines でなく圧縮テキスト**にする。`rs-lib.sh` の出力契約の唯一の例外で、`rs-audit-min.sh` が JSON Lines を畳む出口として振る舞う。逸脱した項目だけを 1 行、detail は既定 60 文字で切り詰め、ヘッダ・集計・次アクション各 1 行。逸脱 2 件で 5 行 / 388 バイトを実測
  7. **安さを文書でなくテストで守る**。`test-rs-audit-min.sh` が「ok / skip / manual を行に出さない」「detail を切り詰める」「出力が 700 バイト未満」を、`test-rs-evidence.sh` が「秘密の値を出さない」「対象外は skip と明示する」を検証する。ここが緩めば簡易版である意味が消えるため、行数・バイト数まで含めて固定する
  8. **コスト目安を README に書く**。スキルの説明だけでは高い方を選び続けてしまう。3 スキルの「何をするか」と実測ベースの目安、そして安い理由の内訳を並べ、使い分けの判断材料を利用者側に置く

- **影響**: repo-standards のスキルは 7 個になり ([0009](0009-plugin-granularity.md) の再議論しきい値は 8)、プラグイン初のサブエージェント定義 (`agents/standards-judge.md`) が入る。`rs-lib.sh` の出力契約に例外ができたため、以降 rs-*.sh を足すときは「JSON Lines を出すか、JSON Lines を畳む出口か、材料を集める側か」を明示する。`rs-evidence.sh` は正本の id ごとに材料収集関数を持つので、setup リポ側で LLM 判定項目を足したときは未実装として degrade する (判定観点だけ渡して収集は判定側に委ねる) — 契約ずれで落とさない代わり、その項目だけコストが跳ねる。簡易版で NG が出ても修正へは直行できず本監査を経由するが、これは意図した非対称。安い層の verdict を findings に持ち込めるようにするなら、判定の出自 (モデル・材料の範囲) を行に記録する設計が先に要る。
