# 0008: GitHub のリポジトリ設定をリポ内の定義で管理し、承認を PR に一元化する

- **状態**: 採用 (2026-08-04)
- **文脈**: 人間側の承認プロセスをできるだけ減らしつつ、作業の記録と根拠は残したい。障害になっていたのは **GitHub のリポジトリ設定が git 管理外**であることだった。設定を変えても diff に出ず PR にも履歴が残らないため、repo-standards は変更のたびに個別の承認を取る設計 (SKILL.md の A 群) になっており、可逆な変更でも人間を待たせていた。一方で個別承認は粒度がばらばら (wiki の無効化と default branch のリネームが同じ重み) で、**承認そのものが形骸化**していた。
  - 代案として、正本の各項目に `apply: auto|confirm|manual` 属性を足して承認の要否を静的に決める案を検討した ([#24](https://github.com/shinyaoguri/claude-plugins/issues/24))。しかし新しい概念 (3 値の属性) と新しい記録先 (適用ログ用の Issue) を増やすことになり、**シンプルさで劣る**と判断して採らなかった
- **決定**:
  - リポジトリ設定の定義を `.github/repo-settings.json` に置き、`scripts/apply-repo-settings.sh` が突き合わせる。設定変更は**この JSON を変える PR** として行う。これにより (1) 変更が diff に現れて根拠とレビューが git 履歴に残り、(2) 承認が PR マージに一元化され (CI green なら merge してよい既定の運用なので実質的に承認ゼロ)、(3) 手で変えられてもドリフトとして検出される
  - スクリプトは**既定が `--check`** (差分ありで exit 1) で、適用は `--apply` の明示が要る。CI (validate ジョブ) は check だけを回す
  - **定義に書いたキーだけを見る**。書いていない設定には触れないので、管理範囲を段階的に広げられる。最初は必須項目に効く範囲 (マージ方式・ブランチ保護 ruleset) に絞る
  - ruleset を読めない環境では**ゲートにしない** (skip して exit 0)。CI のトークン権限は環境によって違い、そこで CI 全体を落とすと本題と無関係な赤が出るため
  - 仕組みの導入と設定内容の変更は別 PR にする。導入時の定義は**現状のスナップショット**とし、個人標準への適合はその後の定義変更 PR で行う (初回から「あるべき値」を書くと、適用するまで CI が赤いまま入らない)
- **影響**: repo-standards の A 群 (GitHub 設定を gh コマンドで適用し承認を取る) は、このリポでは B 群 (リポ内ファイルを変える PR) に吸収される。プラグイン側 SKILL.md の A/B/C 群の扱いは別途見直す。`/repo-audit` は引き続き「個人標準との突き合わせ」を担い、本 ADR の仕組みは「このリポの設定の宣言的管理」を担う (役割が違うので二重管理にはならない)。CI での**自動適用は行わない** — Actions の `GITHUB_TOKEN` では ruleset を変更できず PAT の管理が必要になるため、費用対効果を見て見送った ([#25](https://github.com/shinyaoguri/claude-plugins/issues/25) に論点を記録)。定義と実状の乖離はドリフト検査が検出するので、適用漏れが放置されることはない。
