# 0012: 監査の精度は「根拠の接地・材料の下限・独立した反証」で上げる

- **状態**: 採用 (2026-08-07)
- **文脈**: [0011](0011-audit-cost-tiers.md) で安い層 (repo-audit-min) を作った反対側として、本監査 (repo-audit) の精度を上げる番になった。現行を検証したところ、精度の問題は判定モデルの賢さではなく**判定の記録契約に空いた穴**にあった。3 つとも実測で再現している:

  - **`verdict=ok` を付けても `decision` が `pending` のまま残る**。repo-audit-fix は `list --decision pending` を拾うので、直すものが無い項目まで承認対象に並ぶ。ノイズが混ざるほど承認は雑になる
  - **`verdict` に `skip` が無い** (`ok` / `warn` / `ng` のみ)。判定観点が「対象外なら skip とする」と明示している項目 (`adr-covers-decisions` / `work-log-externalized` / `claude-mcp-config-sane`) を `ok` に丸めるしかなく、**対象外と適合が集計上で同じに見える**
  - **`--evidence` が任意**。根拠なしで `ng` を書き込めるため、後から第三者が検証できない判定が監査記録に残る

  加えて、判定サブエージェントに渡していたのは「対象ファイルのパスと判定観点」だけで、材料は各エージェントが自力で探していた。探索の当たり外れがそのまま判定のばらつきになり、同じリポを再監査しても同じ結論が出る保証がない。そして**単一エージェントの判定がそのまま確定していた** — もっともらしいが誤っている判定を止める仕組みが無かった。

- **決定**:

  1. **判定には根拠を必須にする**。`rs-findings.sh set --verdict` は `--evidence` が 20 バイト未満なら非 0 で拒否する。「ok」「問題なし」のような接地しない根拠を弾くのが目的で、文書ルールでなくスクリプトで強制する。バイトで測るのは `${#var}` も `wc -m` もロケール依存で CI と開発機で基準がずれるため
  2. **`verdict` に `skip` を足す**。判定観点が定義した対象外条件を、適合と区別して記録できるようにする
  3. **`decision` を判定に追従させる**。`ok` / `skip` の項目からは `decision` を落として未決から外し、逆に反証で `ok` → `warn` へ覆った項目は未決へ復帰させる。復帰させないと、覆った項目が修正フローから丸ごと落ちる
  4. **材料の下限を保証する**。判定サブエージェントには `rs-evidence.sh <id>` の出力を渡す。ただし**下限であって上限ではない** — 本監査では実ファイルを読ませ、判定観点が要求する深さまで降りさせる。repo-audit-min との差は「材料が上限か下限か」であって、材料を使うかどうかではない
  5. **独立した反証パスを通す**。`required` 項目と `ng` / `warn` と判定した項目は、別コンテキストの standards-verifier が「覆せるか」を確かめてから確定する。反証係には**まず反対の結論を立てさせ**、迷ったら upheld でなく overturned に倒させる — 誤って厳しく出た判定は修正フローで人が却下できるが、**誤って ok と記録された項目は誰も見に来ない**ため、非対称に倒すのが正しい
  6. **反証の状態を findings に持たせる** (`verified`)。`verdict` を書き換えると落ちる。これでセッションが尽きても `--needs-verify` で続きから入れ、覆した項目を反証済みと取り違えることもない
  7. **振動には上限を置く**。同じ項目が 2 回覆ったら 3 回目を回さず、両論を併記してユーザーに委ねる。判定が振動するのは観点かリポの状態が曖昧なサインで、回し続けても収束しない
  8. **判定係と反証係をプラグインのエージェント定義として持つ**。出力契約 (`VERDICT` / `EVIDENCE` / `RESULT`) と「skip を逃げ道に使わない」「根拠に具体物を含める」といった作法を SKILL.md でなくエージェント側に置き、呼び出しごとに書き直されないようにする

- **影響**: `rs-findings.sh` の行スキーマと `set` の契約が変わるため、repo-standards は minor bump になる (既存の findings は `verified` を持たないだけで読める)。repo-audit のコストは反証ぶん増えるが、[0011](0011-audit-cost-tiers.md) で安い層を用意済みなので「日常は min、腰を据えるときは full」の使い分けで吸収する。プラグインのエージェントは 3 個になる。反証は同じモデル系統の別コンテキストで走るので、**モデル固有の思い込みは反証を通り抜けうる** — 反証は単一判定より強いが万能ではなく、最終的な承認は repo-audit-fix で人が握る前提は変わらない。安い層の判定を findings に持ち込む話 ([#62](https://github.com/shinyaoguri/claude-plugins/issues/62)) は、この `verified` とは別に「どの精度の判定か」を記録する設計が要る。
